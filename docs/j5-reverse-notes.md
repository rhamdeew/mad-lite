# Январь 5.1 (J5V05L19): заметки по разбору прошивки

Дизассемблер: `r2 -a 8051` (radare2). Процессор — Siemens **C509** (8051-совместимый; MDU 0xE9–0xEE, 8 указателей данных через DPSEL 0x92). Источники и сторонняя разметка — `sources.md`.

## Карта памяти образа (64 КБ)

| Область | Что |
|---|---|
| `0x0000–0x5FFF` | код, в т.ч. списки KWP `0x597A…` |
| `0x6000–0x604F` | заголовок: `J5.1` (0x600A), ID ПО (0x6020), дата сборки (0x6030), модель (0x6040) |
| `0x6050–0x9FFF` | калибровки |
| `0xA000–0xFFFF` | код: интерполяция (A59D, A575, A611, A6CD), арифметика (A352, A3ED, A400), протоколы |
| `0xC79x` | блок идентификации для тестера: `1411010-41` / `SAMARA-1.5L,16V` / дата / ID |

## Процедуры интерполяции

| Адрес | Вход | Таблица |
|---|---|---|
| `A59D` | DPTR, R2 = столбец (57h), R3 = строка (5Ch) | 16×16, индекс `(R3 & F0) + (R2 >> 4)`, дробь в младших полубайтах |
| `A575` | DPTR, R2 (0..F0) | 32 точки, индекс `R2 >> 3` |
| `A611` | DPTR, R2 = индекс, R3 = дробь | 1D с интерполяцией |
| `A6CD` | DPTR, A (0..F0) | 16 точек |

## Насколько описание J5V05L19 подходит другим версиям J5 (проверка 26.10.2026)

Прогон по всем 34 серийным образам J5 (`firmware/j5`):

- **Процедура 2D-интерполяции** (тело `A59D` в L19, 24 байта без абсолютных адресов) найдена **во всех** версиях по сигнатуре, но по разным адресам: `A9ED` (J16-9011, M30, N35, A5V05N35), `A995` (L25), `A896` (K22), `A43D` (K17), `4244` (F16), `4497` (H16), `3C59…4287` (J5V13), `49D3` / `B3F7` (J5V26), `4531` (J5V07G26), `4848` / `4932` (J5V07I27/J28). Код в версиях сдвинут.
- **Входы у неё везде одинаковые — `57h` (обороты) и `5Ch` (нагрузка)**: раскладка переменных ОЗУ общая для семейства.
- **Адреса калибровок в основном общие**: 14 ключевых (`613C 6104 6AC8 6CC8 6DC8 6613 6713 6953 7208 6057 71D8 7F67 726D 7877`) адресуются кодом во всех серийных J5V05, J5V03, J5V13, J5V26, J5V07G26 — **кроме J5V07I27/J28 (2112-71, Январь 5.1.2): 5 из 14**, у них другая раскладка.
- **Набор функций разный**: 16–18 вызовов карт в ранних версиях (F16, H16, J5V13, J5V03F–J), 22–26 в поздних (K17+, L25, J5V26L52).
- ~~Генератор привязан к адресам процедур L19~~ — **сделано 27.10.2026**: процедуры по сигнатурам, сетки по коду, имена по месту записи результата; см. раздел «Описания таблиц для всех серийных J5».
- **J5LS** — другая раскладка (автор убрал часть серийных таблиц и добавил свои); описание L19 не применимо, нужен импорт карты `j5ls_v43.j5`.

## Проверка кода на всех прошивках J5 (26.10.2026)

Раньше всё проверялось только на J5V05L19. Прогнаны все 35 образов ПЗУ J5 из `firmware/j5` (тесты `J5AllFirmwareTests`, `J5AllFirmwareSessionTests`; полный прогон в эмуляторе — `VAZ_ALL_FW=1 swift test`, ~3 мин).

| Что | Результат |
|---|---|
| Семейство, КС, блок идентификации | ✅ все 35 |
| Эмулятор: запуск, иммобилизация, связь KWP, двигатель 3000 об/мин, ошибки `18` | ✅ все 35 (ЦН 175–199, впрыск 2,6–4,7 мс, УОЗ 32–37°) |
| Кадр `21 01` | ❌→✅ у 12 прошивок Р83 (-71) другой формат, см. `kwp2000-j5.md`, «Кадр Р83» — исправлено |
| ID ПО | ❌→✅ у 3 прошивок устаревший ID по 0x6020 — исправлено (ниже) |
| Разбор идентификации J5V26K23 | ❌→✅ к полям прилипал байт КС кадра — исправлено (ниже) |

**ID ПО по 0x6020 бывает устаревшим** (подтверждено): `J5V05F16.BIN` → `J5V05F01` (дата сборки 05/01/99), `j5v03f21.bin` → `J5V03F02`, `J5v03h21.abs` → `J5V03G21`. Блок идентификации (`1411010-…`, его ЭБУ отдаёт тестеру) везде совпадает с каталогом сайта. Для J5 приложение теперь берёт ID из блока идентификации. Для J7.2 — по-прежнему из 0x6020: у `A205DM53` в блоке идентификации записано `I205DM53`. `A5V03L25` сама себя называет `A5_03L25` в обоих местах.

**J5V26K23 хранит идентификацию готовыми кадрами ответа** (подтверждено, `0xC56C`): `8C F1 10 5A 94 "1411010-04" КС 00`, далее `91 F1 10 5A 97 "LADA -1.45L, 8V"…`, `5A 99` — дата, `5A 9A` — ID. Байт КС бывает печатным (`d`, `e`, `l`), поэтому длину поля берём из байта формата (`8C` → 12 − 2 = 10 символов). Остальные версии хранят строки через `00`.

**Ошибка «ОЗУ» в ранних версиях при включении** (установлено по коду J5V05H16; что это ОЗУ с постоянным питанием — предположение): F16, F16cond, H16, G21, H21, J5V13F02/H02/I02, J5V07G26 в эмуляторе ставят бит «ОЗУ» (неисправности 1, бит 6). В H16 (`0x157A–0x15BD`): если маркер `[F8C2] ≠ 55h` (холодный старт), считается сумма `1 + Σ XRAM FD00–FEFF + Σ F4A2–F4C1` и сверяется со словом `[F8FE:F8FF]` (`lcall 0x43A2`); не совпало — `setb 22h.6`. Слово `22h` копируется в `5Bh` (`0x36A1 mov 5Bh,22h`) и уходит в кадр. В эмуляторе XRAM пустое, сумма = 1 ≠ 0 — значит, ошибка честная: так же будет на первом включении после потери питания. Поздние версии (I16, J16 и новее) так не делают. Это не ошибка эмулятора.

Прочее: у `j5v03f21` впрыск 2,65 мс против 4,43 у остальных J5V03 при той же ЦН — вероятно, другие калибровки (не проверено).

## Описания таблиц для всех серийных J5 (генератор, 27.10.2026)

`tools/gen_j5_definitions.py --all` пишет описание для каждой сборки из `firmware/catalog.json` в `Sources/VazCore/Definitions/` (31 файл: 29 ID + 3 сборки с тем же ID, но другим кодом). Тесты — `J5DefinitionsTests`.

**Как устроено:**
- **Процедуры интерполяции ищутся по телу** (без абсолютных адресов): 1D (`A575` в L19, сигнатура `EA C4 23 54 1F FB…`), 2D по таблице в ПЗУ (`A59D`, `EB 54 F0 F5 F0 …` + `EC 93`), температурная (`A611`, `EA 93 F8 EA 04 93…`). Есть 2D-двойник для таблиц в ОЗУ (`A62F` в L19: то же начало, но `mov dpl,a; movx`). Вызываются и `lcall`, и `acall` (в ранних версиях почти всегда `acall`) — генератор понимает оба.
- **Вид доступа** — по регистрам перед вызовом: `r2=57h, r3=5Ch` → обороты × нагрузка; `r3` из `mov a,52h|B; movc; mov r3,a` → обороты × ДЗ; 1D по `57h`/`5Ch`; регистры ищутся и до, и после `mov dptr`.
- **Сетки — по коду, который их читает:** обороты — `mov dptr,#X; mov a,54h; movc` (таблица 256 байт до F0), ДЗ — то же с `52h` (101 байт), нагрузка — шаблон «ЦН − слово [X] … × [G]». У **J5V07I27/J28** сетки в других местах: ДЗ `720A`, нагрузка `60BD`/`60BA` (у остальных — `7208`, `6064`/`6066`, обороты везде `613C`).
- **Имена:** из `KNOWN` (ручной разбор L19) — только если в сборке **те же адреса сеток** и код читает адрес **тем же видом доступа**; `confirmed` при переносе понижается до `likely`, в пояснении — «по аналогии с J5V05L19». Иначе — **по месту записи результата**: `62h` → УОЗ (E/2), `60h` → состав смеси (AFR), `6Fh` → коэффициент коррекции (`confidence: auto`). У J5V07I27/J28 имена только у сеток и по месту записи.
- **Один ID — разный код:** J5V05J16 и его сборка под HIP9011 (код как у N35), J5V05K17 и K17a, J5V05F16 и F16cond — отдельные файлы `ID~файл.json`. В каждом описании — **контрольные байты** (адреса процедур и их начало); приложение берёт описание, только если они на месте (`CalibrationDefinition.matches`).

**Проверка:** у всех 35 образов описание находится; сетки монотонны и правдоподобны (обороты 600…7470, ДЗ 0…98); карты с именем «УОЗ» — в пределах −20…70°, AFR — 8…20. Сверка с картами CTP: **J5V05N35 — форма и оси совпали у 91 из 98** общих таблиц, **J5V03K22 — у 75 из 80**. Расхождения: кривые, обрезанные по следующей ссылке кода (`6FE4` 33 против 39, `9992`, `928A`, `900D`), карта зон `63D3` (у нас строки по нагрузке, в CTP — по ДЗ), `76EF` (у нас константа), `6104` (у нас 51 точка — подтверждено по L19). По сравнению с прежним описанием L19 генератор нашёл ещё `87E4` (кривая по ТОЖ; в CTP — состав смеси на ХХ) и оси у `7CF7` (обороты × ДЗ; в CTP — поправка ЦН) и `977D`.

**Названия из карт CTP (27.10.2026, `tools/ctp_map.py`).** Для сборок с раскладкой L19 генератор переносит из карт серийных J5V05N35 и J5V03K22 (`firmware/maps/`; для J5V03 и A5_03 первой берётся карта K22, для остальных N35) имя, раздел (папку карты), единицы, пересчёт, знак и форму:
- таблицы из ручного разбора (`KNOWN`, не `auto`) сохраняют наши имя, форму и масштаб — например, `7F67` остаётся с делителем 128 (по коду), `6104` — 51 точка; из карты берётся только знак при совпадающем масштабе (карты УОЗ стали `s8`; кадр диагностики тоже передаёт УОЗ со знаком) и название карты в пояснение;
- наши догадки и автоматические таблицы получают всё из карты, если форма совместима (та же, кривая другой длины или «константа», которая в карте — таблица, как `76EF`); при несовместимой форме — только пометка;
- таблицы и байты флагов, которых нет в описании, добавляются, **только если код сборки читает адрес** (старые сборки могут не иметь функций из карт 2002–2004 гг.);
- `confidence: likely`, пояснение «По карте CTP J5V05N35: «…»».

## Расчёт времени впрыска (0x1B56–0x1D88)

```
ЦН (F82E, мг·6)
  → подача = ЦН·256 / (AFR+128)             MDU-деление, AFR = 61h из карт 6613/6713/6953
  → × F97F → F837 (подача на цикл), не меньше пусковой F89B
  → модель плёнки по цилиндрам F839[41h]:   осаждение 6F0F(нагрузка) × 6F2F(ТОЖ), сброс 7CD7
  → + F97B
  → × (6Fh+128)/256                          коэф. коррекции: карта 6813 без ДК, регулятор с ДК
  → × (77h+128)/256                          карта 8E2A только на ХХ (2Bh.1), иначе 1,0
  → × [6057] / 256                           масштаб подачи → время (форсунки)
  → F987 (без задержки)
  → + 50h                                    задержка форсунки 71D8 по напряжению F978
  → не меньше [5FA8:5FA9] (0x00C8 = 1,6 мс)
  → F841 (E/125 мс)
```

Подача умножается на `F97F/128` (обогащение при прогреве, ниже), к ней прибавляется `F97B` (ускорение, ниже).

Отсечка: при `54h ≥ [605C]` (обороты ≥ 6210) или флаге 2Bh.3 подача = 0.

Пуск (0x1A2D, бит 2Ah.5): 710B(ТОЖ) × 7132 × 7A77(ДЗ, продувка) × 7A87(циклы F89E/8) × [FFC0] → F89B.

## Обогащение при прогреве (0x3FF0–0x4041)

```
F97F = 0x80 + ((7F67[F887,F888] − 0x80) · 8193[(7208[ДЗ]+8)>>4 , 59h]) >> 8
подача × F97F / 128
```

- `7F67` — 39 точек по ТОЖ (−40 °C, шаг 5), FF на холодном → 0x80 (1,0) к ~+60 °C. Интерполяция A611 по `F887` = (ТОЖ+40)/5 и дроби `F888`. `7F75` — отдельная ссылка на хвост этой же таблицы.
- `8193` — 16×16 без интерполяции, строки по дросселю, столбцы по оборотам (59h); вес 0…255/256. 0 на высоких оборотах — там прогревное обогащение выключено.
- Рядом: `7F07`, `7F27`, `7F47` (кривые по оборотам 58h) → `F943`, `F953`, `F954` — назначение не выяснено.

## Обогащение при ускорении и обеднение при сбросе (0x1800–0x1970)

```
r2 = 75EF[57h, 7208[ДЗ]]               наполнение по ДЗ (обороты × дроссель)
F98C (текущее) vs F8B8 (прошлое) — направление изменения:
  рост:  прирост = r2 − F8AB; если > [6054]:  F97D = прирост · 8393[ТОЖ];  F97B = max(F97B, F97D)
         иначе F97B затухает: × [5F6B]/256 (или × [5F6C]/256)
  сброс: прирост = F8AB − r2; если > [5F74]:  F98F = прирост · [5F73];  затухание F98D × [5F75] / [5F76]
F8AB = r2
```

`F97B` прибавляется к подаче перед коэффициентами коррекции (0x1CFA).

## Обучение смеси в ОЗУ `FD00–FEFF` (27.10.2026)

Разобрано по J5V05L19; у всех серийных J5 тот же код (поиск по сигнатурам, 33 образа). Это ОЗУ с постоянным питанием: блок держит его вместе с `F4D2` (40h байт) под своей контрольной суммой (`0x22A6`, `0x3BD1`, `0x51E2`), при ошибке — сброс.

| Что | Где в L19 | Как |
|---|---|---|
| **`FD00`** — таблица обучения 16×16 | чтение `0x488B` | интерполятор по XRAM (`A62F`), столбцы — обороты (57h), строки — нагрузка (5Ch). Результат + быстрый регулятор по ДК (6Eh) → **6Fh**, коэффициент коррекции в кадре `21 01` |
| **`FE00`** — та же таблица при продувке адсорбера | `0x2916` | `FE00[i] = FD00[i] + 76EF[i]` (поправка при продувке, со знаком); на холодном (49h ниже порога) — просто копия `FD00`. Читается вместо `FD00` при бите 5Eh |
| Обучение | `0x9D44` | ячейка 5Fh (нагрузка·16 + обороты) ±1 за шаг, предел 00/FF; страница FD или FE — по биту 64h (= 5Eh) |
| Сброс | `0x9DAC` | `FD00[i] = 6813[i]` («коэффициент коррекции без ДК»; во всех серийных `80h` = 1,0). У J5V07I27/J28 — из `6713` |

Значение ячейки — (E+128)/256, как у 6Fh: `80h` = 1,0, `90h` = 1,0625 (+6 % топлива). Блок прибавляет там, где смесь без поправки бедная, и убавляет, где богатая.

`FE80–FE89` портит аварийный обработчик (`0xE9DE`): сохраняет туда адрес, на котором остановился, и зависает до сторожевого таймера. После такого сброса эти 10 ячеек второй таблицы — не обучение.

**J5LS N35 и V2:** строки таблицы — **по дросселю** (`7208[52h]`, `0x3561` / `0x4777`), столбцы — обороты; сброс заполняет `80h` (`0x44C4`, N35), а не копирует карту. В эмуляторе у N35 страница `FE00` после включения — нули, и при продувке коэффициент падает до 0,56 (предел `0Fh`) — на живом блоке не проверено.

В программе — `AdaptationMap` (карта на вкладке «Диагностика» после «Снимка блока»). Обучение в эмуляторе воспроизвести не удалось: при застывшем бедном ДК блок за 2 мин выходит из регулирования, ячейки не меняются.

## Принудительный холостой ход (0x4440–0x4620)

- Номер режима в `6Bh` (0, 1, 2, 3, 4…). Переходы зависят от скорости `F8AE` против `[607B]`, оборотов `54h` против `[60E9]` (40 = 1200 об/мин) и `[60EA]`, счётчика `6Ch` против `[608E]`.
- В режиме ПХХ ставится бит `2Bh.3` («признак блокировки подачи топлива» в кадре KWP) — расчёт впрыска при нём даёт 0 (см. 0x1B56).
- В режимах 2/4 УОЗ берётся из `6FC4` по оборотам (58h) → `62h`.

## Замещающие значения при неисправностях

- ДТОЖ (флаги `23h.3`/`24h.3` — по протоколу KWP «низкий/высокий уровень сигнала ДТОЖ», подтверждает догадку): `49h` = `7DF7[F8AC >> 4]` — модель прогрева по времени, 0x3C (20 °C) → 0x87 (95 °C).

## Сторож потока расчёта и софт-рестарт (установлено 26.10.2026, эмулятор)

confidence: confirmed (наблюдение на J5V05L19 в эмуляторе; на живом блоке не проверено).

- Счётчики IRAM `3C/3D` (обычные ячейки ОЗУ) — сторож «расчёт жив». Перезаряжаются обработчиком EX0: `0x02F4` `mov 3C,3E`, `0x02F7` `mov 3D,3F`.
- Проверка в главном цикле: `0x4912–0x4949` (вызывается из `0x3DB2`). Условия рестарта: `3D ≥ 4` (`0x493B–0x4940`) или `3C ≥ 30` (`0x4942–0x4947`).
- ~~Следствие: если расчёт по зубьям не завершается, ЭБУ рестартится периодически (~2,35 с без вращения; ~1,1 с при вращении)…~~ **Неверно (исправлено 26.10.2026).** Рестарты в эмуляторе были вызваны **ошибкой ядра CPU эмулятора**, а не логикой прошивки и не отсутствием compare-таймеров: инструкции `orl c,bit` / `anl c,bit` (и с `/bit`) при «решённом» значении C не считывали байт адреса бита (короткое вычисление `||`/`&&` в Swift), и этот байт исполнялся как опкод. В `0x276D` (`orl c,22h.6`, байт `16h`) он превращался в `dec @R0` с R0 = `BEh` и сбивал указатель кольцевого буфера (см. ниже) на нечётный; буфер «уезжал» в младшие адреса IRAM и на t+3,5 с затирал `3C/3D` → рестарт. После исправления ядра рестартов нет ни без вращения, ни при вращении, ни при «тёплом» наборе (проверено 8 с эмуляции). Сам механизм сторожа описан верно.
- **`0x218D` — общая процедура инициализации**, а не только «софт-рестарт». Три входа:
  1. сброс от аппаратного сторожа: вектор `0x0000` → `0x204D`, там читается `IP0.6` — в C509 это флаг **WDTS** «сброс был от сторожа» (рядом `IP0.7` = OWDS; manual, гл. 8); при установленном WDTS → `0x2054` → `0x218D`, при сброшенном — обычная загрузка с `0x2057`;
  2. программный рестарт: `ljmp 0x218D` из `0x4949` (сторож потока) и `0x208D`;
  3. проверка ОЗУ при включении (`0x2080–0x208D`): если `[F8C2] ≠ 55h` и бит `[F4C5].5` сброшен — сначала `setb 2Dh.3`, затем `0x218D`.
- Начало `0x218D`: `mov WDTREL(86h),#0E2h`, `setb IEN0.6` (бит **WDT** — разрешение обновления сторожа), `setb IEN1.6` (бит **SWDT** — запуск сторожа) и только затем `clr EA`, `SP=C2`. То есть аппаратный сторож запускается при каждом прохождении инициализации (при обычной загрузке — `WDTREL=80h` на `0x205A`). WDT у нас не эмулируется, но его биты видны в SFR.
- Очистка ОЗУ при `0x218D`: циклы `0x21AB` (0x01–0x2C) и `0x21B1` (0x2E–0xFF). Ячейка `2Dh` очищается только маской `anl 2Dh,#1Fh` (`0x21A8`) — её **младшие 5 бит переживают рестарт**; судя по `setb 2Dh.3` на входе № 3, это флаг причины рестарта (какие биты что значат — не проверено, предположение).
- В самой инициализации есть запись `S0BUF←0` (`0x222F`) — при каждом рестарте на K-линию выходит нулевой байт. PC в `0x0000` при программном рестарте не попадает — трассировщики, ловящие только вектор ресета, рестарт не видят.

## Кольцевой буфер периодов в EX0 (0x0301–0x0345)

confidence: confirmed (код + эмулятор).

- В EX0, после перезарядки сторожа: `38h:39h = R2:R3 − 36h:37h` (банк 3: время текущего зуба минус сохранённое — период между событиями синхронизации), бит `2Dh.7` ← `P8.0` (`DDh`, бит 0; назначение входа не выяснено).
- Пара `38h/39h` пишется в **кольцевой буфер IRAM `B0h…BDh`** (7 записей по 2 байта, косвенная адресация — верхние 128 байт IRAM). Указатель — IRAM `BEh` (косвенно), шаг 2, при `≥ BEh` возвращается на `B0h`; инициализация `BEh ← B0h` в `0x26D9`. Указатель копируется ещё и в XRAM `F9D5` (страница DPSEL=5), смещение от `B0h` используется как индекс в таблице XRAM `F9C7…`.
- Защиты от нечётного указателя нет: при сбое он проходит по всей IRAM (так проявилась ошибка эмулятора выше).

## Иммобилайзер: блокировка пуска (0x5100–0x5142, 0xC0A2–0xC27B)

confidence: confirmed для J5V05L19 в эмуляторе (на блоке не проверено).

- Признак «иммобилайзер обучен» — `2Dh.2`, ставится при чтении EEPROM в `0xBA61`: `2Dh.2 = NOT F47D.7`, `2Dh.4 = NOT F47D.6`.
- Пока иммобилайзер молчит, ЭБУ шлёт `A0 03` (обучен) / `A0 02` (не обучен), после 4 попыток (`F4B6 = 4`, `0xC099`) переходит на `A0 07` / `A0 06`. При обученном (`2Dh.2 = 1`) и без ответа `0xC0BC` сбрасывает `2Dh.3`, `0xC274` — `2Dh.1` (заодно `clr REN0` и `IEN3.3` — тик 0,5 мс).

## EEPROM (I²C, 24Cxx) — процедуры и раскладка

confidence: процедуры и выводы — confirmed (код + эмулятор); размер микросхемы — предположение.

- Шина программная: **SCL = P3.3, SDA = P1.5**. Порты работают в двунаправленном режиме (`orl SYSCON,#40h` — PMOD, `0x21E9`); для чтения SDA прошивка делает вывод входом через двойную инструкцию `orl IP1,#80h` (PDIR) + `orl P1,#20h` (это запись в DIR1, а не в защёлку), обратно — `anl P1,#DFh` после PDIR.
- Процедуры: `0xB08E` START, `0xB0BD` STOP, `0xB0EA` передать байт R4 (C = NACK), `0xB12E` принять байт в R4 (C на входе = 1 → NACK последнего), `0xB17C` чтение блока (R4 — адрес, R1 — число байт, @R0 — куда; адрес устройства `A0/A1`), `0xB1B8` запись блока (`A0`), `0xB1E4` — то же с `A2` (вторые 256 байт, т. е. микросхема не меньше 24C04). Перед обменом `WDTREL ← 80h` и обновление сторожа.
- Адреса `02…07`: пара `[F47C, F47D]` трижды, голосование 2 из 3 (`0xBA08–0xBA60`); ошибка чтения (NACK) → `setb 22h.2`. `F47D.7 = 0` — иммобилайзер обучен (см. выше). У пустой EEPROM (`FF`) иммобилайзер не обучен — так ведёт себя новый блок (предположение по логике кода).

## Контрольная сумма ПЗУ (Январь 5.1 и 7.2, образ 64 КБ)

**Алгоритм:** 16-битная сумма всех 65 536 байт образа должна равняться слову по адресу `0xFFFE` (little-endian). Слово `0xFFFA` — **зеркало**: побитовая инверсия КС. Четыре байта КС и зеркала в сумме всегда дают `0x1FE`, поэтому

```
КС     = (сумма всех байт, кроме FFFA, FFFB, FFFE, FFFF) + 0x1FE   (mod 65536)
зеркало = ~КС
```

| Где | Что |
|---|---|
| `0xE41B` (J5V05L19) | проверка при старте: сумма 0x0000…0xFFFF, сравнение с `[FFFE]`; при несовпадении бит `20h.3` |
| `0x527B` | фоновый пересчёт → `F8F8` (КС ПЗУ в кадре KWP, байты 35–36), сравнение с `[FFFE]`; при несовпадении бит `22h.7` |
| `0xFFFE–0xFFFF` | КС (публикуется как «КС #7602») |
| `0xFFFA–0xFFFB` | зеркало `~КС` (у J5V05L19: `FD 89` = `~0x7602`) |
| `0xFFF0–0xFFF9`, `0xFFFC–0xFFFD` | нули в заводских образах |

Код J5V05L19 зеркало не читает (ссылок на `FFFA` нет), но заводские образы и инструменты его поддерживают — сохраняем.

Проверено:
- 61 из 61 сырых образов 64 КБ (J5 и J7.2): сумма = КС и зеркало = ~КС (тест `ChecksumTests.allFactoryImagesAreValid`).
- 20 опубликованных на chiptuner.ru значений КС совпадают со словом `FFFE`. Расхождения — у «a»-версий (сайт даёт КС оригинала) и у J5V03F21, J5V07G26, J5V07J28 (файлы отличаются от официальных).
- Зеркало и формулу `+0x1FE` подсказал скрипт `j7_checksum.py` из сводки пользователя (проверен им на I205DM53).
- **Частичные суммы** калибровок (`sum(6000–7FFF)` → `0x5EBD`, `sum(8000–9FFF)` → `0xCA05`) из того же скрипта подтверждаются **только у I205DM53**; у остальных 25 образов J7.2 и у J5 их нет. Это особенность отдельных версий — искать по коду для каждой.

**Исправление после правки** (`Checksum.fix`): записать `КС = expected` в `0xFFFE` и `~КС` в `0xFFFA`. Других байт не трогает; КС меняется вместе с содержимым.

> Исправлено 26.10.2026: первая версия считала `0xFFFA` «компенсатором» и подгоняла сумму байтами `0xFFF0–0xFFFD`, сохраняя старую КС. Это ломало зеркало — заменено заводской схемой.

Как устроен вариант J5V05L19a (контроль ПЗУ отключён): КС `7602` сохранена, сумма подогнана байтами `FFFC–FFFD` = `F2 94` и `F294` = `9D`.

## Таблица ДМРВ: код АЦП → расход воздуха (27.10.2026)

Найдена по тюнинговым `J5V07G26-538/-3855` («тарировки Сименс»): от серийной G26 они отличаются блоком `4EDD–50DC` и почти ничем в коде.

- **Где:** процедура опроса АЦП (`0x0695` в G26) читает результат канала ДМРВ из `ADDAT` (`D9h`) и берёт два байта: младший из `[T + код]`, старший из `[T + 100h + код]` (`inc DPH`). Сумма копится в `30h/31h`. Таблица — 256 слов, разложенных на две страницы по 256 байт.
- **Поиск во всех прошивках:** `90 TT TT 93 C3 C2 AF 25 30` (`mov dptr,#T; movc; clr c; clr EA; add a,30h`). Найдена во **всех 35 серийных J5**, в J5LS N35/V2 и в 3 образах `j5other`. Нет только в прошивках на ДАД `j5map` — там ДМРВ нет. Адрес `T` у каждой сборки свой: L19 `99B9`, G26 `4EDD`, I02 `46BB`, I27 `5435`, J28 `5529`, K17 `98F2`, N35/M30 `9D7C`, L25 `9E4A`, K23 `561E`, L52 `A7E0`, J5LS N35 `99E0`, J5LS V2 `99B9`.
- **Значения:** возрастают у всех. У 34 из 35 серийных таблица одна и та же: код 0 → 655, 128 → 1665, 255 → 8380. **У J5V05F16 своя:** 623 / 1750 / 9440 — другой ДМРВ или более ранняя тарировка. В «Сименс»-вариантах G26: 1001 / 1823 / 6955 (`-538`) и 1000 / 1850 / 7800 (`-3855`).
- **Единицы — кг/ч ×10** (установлено по коду 27.10.2026, L19). Процедура АЦП копит сумму значений в `30h/31h` и число замеров в `32h`. По метке оборота (`0x02D6`) копирует их в `34h/35h/33h`. В `0x153F` сумма делится на число замеров делителем MDU C509 (`MD0/MD1 ÷ MD4/MD5`), и частное пишется в `F808`. `F808` уходит в кадр `21 01` как «расход воздуха, E/10 кг/ч». Значит, у серийной таблицы: код 0 → 65,5 кг/ч, 128 → 166,5, 255 → 838. Ось в описании — напряжение `код × 0,01955 В` (10-битный АЦП, опорное 5 В, читаются старшие 8 бит — как в эмуляторе). Сразу за таблицей L19 (`9BB9`) начинается код (`lcall 0x9BB9` в `0x15C6`).
- **В описаниях таблиц — с 27.10.2026.** `gen_j5_definitions.py` ищет таблицу по сигнатуре в каждой сборке и добавляет её в группу «Датчики» (`dataType: u16split` — новый тип: младшие байты всех ячеек, затем старшие). Попутно исправлено: у J5V05K17/K17a на этом адресе (`98F2`/`9912`) раньше стояло имя из карты CTP N35 «Коэффициент уставки РХХ» — это было **неверно**, там таблица ДМРВ. Тесты: таблица есть в каждой серийной J5, возрастает, у всех кроме F16 значения 65,5 / 166,5 / 838; запись меняет обе страницы.
