# Прошивка Январь 5.1 по K-line (этап 5)

> **Внимание.** На блоке с защитой от копирования (её ставят программаторы коммерческих прошивок) вход в загрузчик, даже только для чтения, может стереть прошивку и часть EEPROM. Обнаружить защиту заранее по K-line нельзя. Если блок настраивал калибровщик, сначала спросите его. Вы действуете на свой риск.

Своим загрузчиком через FTDI-кабель, без CAR-CD и Комбилоадера. Источник протокола — Infineon C509-L User's Manual 1997-11, гл. 3.4 (режимы памяти) и гл. 10 (Bootstrap Loader), текст — `docs/vendor/m509.txt`.

## Как это устроено

1. **Вход.** +12 В на вывод 47 («запрос программирования», через делитель на ногу PRGEN процессора) **до** включения зажигания. При сбросе с PRGEN = 1 процессор запускает загрузчик из своего boot ROM (0000–01FF), а не прошивку.
2. **Фаза I.** Загрузчик ищет «инфо-блок» `23 03 33 13` на `C000`, затем `6000`; если он есть и его КС сходится — запускает код из флеш (так блок «закрывают» от чтения). В серийной L19 и в J5LS V43 инфо-блока нет (проверено `BootstrapLoader.lockingInfoBlock`).
3. **Фаза II.** Хост шлёт `00` на любой скорости (8N2), загрузчик меряет её и отвечает `55`.
4. **Фаза III.** Блоки `тип + данные + XOR`; ответы `55` / `FE` (КС) / `FF` (тип). Режим 0 — код в XRAM `F400–FFFF`, 1 — запуск из XRAM, 2 — проверка КС области флеш, 3 — прыжок во флеш.
5. **Агент.** Режим 1 ставит SWAP при PRGEN1 = 1 — «режим программирования»: XRAM становится памятью программ, а **внешняя флеш — памятью данных (MOVX), доступной на запись**. Наш агент в XRAM читает флеш `movx a,@dptr` и отдаёт по UART.

## Флеш

**Подтверждено схемой** «Контроллер системы управления двигателем Январь-5.1, 2112-1411020-41/261 3763 000-01 Э3» (УПЭ ГенДР / ЭЛКАР; `docs/vendor/schematics/jan_5.1-41.jpg`): флеш **DD2 = AM29F010** (128 КБ, 5 В, 8 секторов по 16 КБ, команды JEDEC `AA→5555, 55→2AAA, …`). Адрес A0–A7 через защёлку 74HC573 (DD3), A8–A15 — порт 2, **A16 — P6.0**; WE — P6.3/WRF, OE — RDF (PSEN/RDF), CE — через R25. Процессор DD4 — SAF80C509. Вывод 47 разъёма — «вход разрешения программирования РП» → PRGEN. Значит банк 64 КБ выбирается ногой **P6.0** (двухрежимные прошивки) — агенту нужно её выставлять; чем её держит загрузчик после сброса — не проверено.

**Подтверждено чужим рабочим загрузчиком:** `LOADER.EXE` — «Загрузчик для контроллера "Январь 5.X"», А. Соколов, 2000–2001, v1.10 (DOS; из `…/Чип тюнинг/loader январь 5.zip`; не запускался, разобран статически). В него вшит агент 8051 (файл `0x96F8…0x98D5` → XRAM `F400`, копия — `docs/vendor/sokolov_loader_agent_F400.bin`), его разбор:
- `F400: ljmp F413` — старт; `F410: ljmp F4CF` — вектор SINT0 (как в руководстве: загрузчик переадресует его на `F410`); обмен — по прерыванию UART, скорость остаётся от синхронизации загрузчика;
- команды из 4 байт: `'r'`/`'w'`/`'e'`/`'g'` + адрес (hi, lo) + данные; ответы чтения «замешаны» XOR с ключом (`30h`) и байтами адреса — простая защита протокола;
- **запись байта — AMD: `AA→5555, 55→2AAA, A0→5555`, затем байт; стирание всего чипа — `AA, 55, 80, AA, 55, 10→5555`** (секторное стирание не используется);
- `'g'` — выход без сброса: `anl SYSCON1,#FA` (сброс PRGEN1 и SWAP), `orl SYSCON1,#80` (ESWC), `orl SYSCON1,#40` (SWC), `ljmp 0000` — запуск записанной прошивки;
- линией A16 (P6.0) не управляет; readme: «правильная длина файла — 65536 байт» — работает с одним банком.
- Readme: вход в режим — зажигание при +12 В на 47; если главное реле **не** включилось — блок в режиме программирования. Иммобилайзер, по словам автора, «отрубает K-линию».

## Допущения (проверить на живом блоке)

- `blocklength` в заголовке режима 0 считаем **с** байтами типа и КС (по описанию GetBlock: R7 байт, последний — КС; заголовок принимается с R7 = 8). Наша модель устроена так же, поэтому тест это не ловит.
- КС режима 2 сравнивается с байтами по `start + length + 1` и `+ 2` — как написано в руководстве (возможно, опечатка вместо `+0/+1`).
- Модель отвечает мгновенно; настоящий загрузчик — со временем байта. Агент оставляет UART в режиме 3 на скорости синхронизации.
- K-line полудуплекс: эхо кабеля `BootstrapClient` пропускает (`echoesWrites`). Последовательный порт сейчас открывается 8N1 — **для загрузчика нужен 8N2** (добавить в `SerialKLineTransport`).

## Заметки по модели флеш (28.10.2026)

- В модели `Flash29F010` фаза данных программирования (`.program`) проверяется **до** команды сброса `0xF0`: иначе data-байт `0xF0` при записи воспринимался как «reset» и ячейка не записывалась (ловушка при разработке агента записи — исправлено).
- В системе команд 8051 **нет** инструкции `CJNE A,Rn` (опкод `B8+n` — это `CJNE Rn,#data,rel`). Сравнение A с Rn в агенте — через `xrl A,Rn` + `jnz`.

## Детектирование защиты от чтения (28.10.2026)

Как не потерять коммерческую прошивку при чтении:
- На C509 защита от чтения «по проводу» может быть только **инфо-блоком** загрузчика (`23 03 33 13` на `0x6000`/`0xC000`): на фазе I процессор запускает код из флеш вместо связи. Если это код-«вытиратель», он срабатывает **в момент входа в режим программирования**, до любой связи → предотвратить программно нельзя, обнаружить заранее нельзя.
- **Косвенные гарантии, которые есть:** (1) если синхронизация загрузчика прошла (пришёл `55`), перехвата на фазе I не было → чтение безопасно; если нет — `synchronize()` бросает ошибку и чтение останавливается, без повторов. (2) В прочитанном образе ищем инфо-блок (`BootstrapLoader.lockingInfoBlock`) и показываем предупреждение (`FlashReadModel.Result.infoBlock`).
- Программаторы коммерческих прошивок могут сами ставить такой вытиратель: стирается флеш и часть EEPROM. Для блока, прошитого таким программатором, защита вполне возможна. Безопасная проверка — только чтение микросхемы флеш внешним программатором (байты по `0xC000` и `0x6000`).
- **Главная защита — организационная:** чтение только читает; первый блок — запасной; перед чтением рабочего блока уточнить у калибровщика, стоит ли «защита от считывания».

## EEPROM и иммобилайзер (28.10.2026)

- **Чип:** NM24C04 (DD6 на схеме, 512 Б, два блока по 256), I²C: SCL P3.3, SDA P1.5, адрес устройства A0h (блок 1 — A2h). Шина открытый коллектор; эмулятор моделирует её через защёлку + проводное И (`I2CEEPROM`).
- **Агент EEPROM** (`Sources/VazCore/Flash/EEPROMAgent.swift`): грузится загрузчиком как флеш-агент, сам бит-бэнгом говорит по I²C (не зависит от прошивки в флеш). Команды: `'r' dev addr count` → байты + XOR; `'w' dev addr count data…` → запись + XOR. Чтение — случайное (START, dev write, адрес, повторный START, dev read, N× приём+ACK/NACK). Хост (`readEEPROM`/`writeEEPROM`) ходит блоками по 128 байт, адрес слова и блок считаются по глобальному смещению. Проверено в эмуляторе: чтение 512 Б совпадает побайтно; запись отвязанной копии читается обратно.
- **Отвязка иммо** (`Immobilizer`): `isTrained`/`needsDefeat`/`defeat` по байтам `02…07` (`F47D.7=0` = обучен). `defeat` ставит `02…07 = FF` → не обучен. Проверено в эмуляторе (L19): обученный блок глохнет (обороты 0), после `defeat` заводится. Порядок на живом блоке: прочитать EEPROM → сохранить оригинал → `defeat` → записать копию.
- **ACK-poll при записи EEPROM — сделано:** после STOP агент опрашивает адрес устройства, пока чип не подтвердит (на реальном чипе — конец внутреннего цикла ~5 мс; в эмуляторе мгновенно), ограничено 256 попытками. `programEEPROM` = запись + сверка чтением.
- **Для реального железа (осталось):** тайминги I²C (сейчас без задержек между фронтами — на реальном чипе добавить nop'ы); первый запуск — только на запасном блоке.

## Сквозная проверка пайплайна (28.10.2026)

`BuildAndFlashTests` (эмулятор) — весь путь сборки своей базы:
1. Чистый J5LS V43 → флаги ДАД 40 / ДТВ 44 (`5F07|=0C`, `6051|=10`, наклон `60D2`=65,88) → `Checksum.fix` → заливка загрузчиком (`programImage`: стирание+запись+сверка) в блок, где был N35 → **залитый образ запускается как ЭБУ, мотор крутит 2000, ДАД читается на выводе 40 (≈100 кПа)**.
2. Блок с обученным иммо → `readEEPROM` → `Immobilizer.defeat` → `programEEPROM` → **прошивка с отвязанной EEPROM заводится (не блокируется иммо)**.

Это доказывает, что редактор + загрузчик + агенты + отвязка иммо работают вместе, а не только по отдельности.


## Первое чтение живого блока — 31.10.2026

Запасной Январь 5.1 `2112-1411020-41` на стендовом шнуре (18, 19, 27, 37, 47, 55; 47 постоянно на плюсе, кнопка — питание), KKL FT232RL, 9600 8N2. Результат: флеш `01 20` (Am29F010), образ **J5V05N35**, байт в байт как `firmware/j5/j5v05n35/J5V05N35.bin`. **Подтверждено:** вход в загрузчик по +12 В на 47, синхронизация `00`→`55`, загрузка агента режимом 0 и запуск режимом 1, `movx` из флеш при SWAP, ответ агента `A5`.

Что выяснилось (confirmed на живом блоке):
- **Загрузчик подстраивается под первый байт после сброса.** Если до него в линию шли «Проверить кабель» (10400) или инициализация KWP — он молчит до перезапуска питания. Поэтому `BootstrapClient.waitForLoader` шлёт `00` каждые 0,2 с до 60 с, а блок включают уже после нажатия «Начать». При включении бывает один «мусорный» `00` перед `55` — пропускается.
- **TI0 после загрузчика взведён.** Агенты писали `putc` как «записать S0BUF → ждать TI»; с уже взведённым TI первый `putc` после `A5` возвращался сразу, и следующий байт затирал его — ID флеш приходил одним байтом. Теперь `putc` = «ждать TI → сбросить → записать», а агент на входе делает `setb TI`. Эмулятор (`BootstrapEmulator.enterProgrammingMode`) оставляет TI0 = 1, как живой блок.
- Скорость: 64 КБ с XOR по блокам 4 КБ — ≈80 с.
- **Эхо самого блока.** K-line однопроводная — блок слышит свои байты. После ответа в S0BUF остаётся эхо **последнего** отправленного байта с RI0 = 1 (наблюдение: XOR блока C000 у J5V05N35 = `52` = `'R'`, агент принял его за команду и сбил чтение D000 — «ожидалось 4097, получено 16»; повторено эмулятором). Первая версия чтения из приложения 31.10 упала на этом; скрипт проходил за счёт повторов. Исправлено: в начале цикла команд агенты зовут `dropEcho` (ждать TI, ~0,8 мс, сбросить RI). Эмулятор моделирует эхо (`C509Board.echoesTransmit`), тест `ownEchoIsNotACommand`.
- **Итог 31.10.2026:** чтение из приложения (окно «Прочитать прошивку», ожидание блока + `dropEcho`) прошло с первого раза: J5V05N35, КС 3F4B верная, образ байт в байт как в первом чтении — confirmed.
- **I²C агента EEPROM — тайминги (31.10.2026, до первого живого чтения):** без пауз SCL ≈0,4 мкс в «1» — для 24C04 (100 кГц: tHIGH ≥ 4 мкс, tLOW ≥ 4,7 мкс, tAA ≤ 3,5 мкс) слишком быстро; эмулятор этого не ловит. Теперь после каждого фронта `i2cDelay` ≈5 мкс (14 машинных циклов по 375 нс). ACK-опрос после записи байта — до 256 попыток × ≈0,2 мс ≈ 50 мс (хватает на цикл записи 5–10 мс). На живом блоке **не проверено**.
- **EEPROM живого блока прочитан 31.10.2026** (агент EEPROM с паузами I²C ≈5 мкс — работает на живой 24C04, confirmed): иммобилайзер не обучен, раскладка — `j5-reverse-notes.md`, «Живая EEPROM».
- **Открытый вопрос:** первые две попытки чтения EEPROM из приложения сорвались на «блок 1» (загрузчик подтвердил заголовок, на первый пакет кода ответа нет). Те же пакеты из скрипта (`loadprobe.py`: запись блока, приём 1 с) прошли все, и третья попытка из приложения — уже через `TracingTransport` (короткие чтения побайтно) — тоже прошла. **Причина найдена по трассе (21:02, теперь сорвалось и чтение флеш на «блок 1»):** приложение слало следующий пакет через 0 мс после `55` загрузчика; эхо пакета приходило целиком, а подтверждения не было — загрузчик ещё не слушает и теряет начало пакета. Скрипт ждал ~1 с после каждого ответа. Исправление: `BootstrapClient.interBlockPause` = 100 мс перед каждым пакетом режимов 0 и 1 (значение с запасом, минимум не измерен). Ранние удачные загрузки из приложения — везение по таймингу. `TracingTransport` оставлен включённым в окне чтения: при ошибке в лог загрузчика пишутся последние 40 событий линии (`phase: trace`).
- **Проверено 31.10.2026 21:11–21:12** (после паузы 100 мс): прошивка и EEPROM прочитаны из приложения подряд с первой попытки, оба файла байт в байт совпали с первым чтением — второе независимое чтение EEPROM подтверждает его содержимое (confirmed).

## Безопасная запись — разбор перед первой живой записью (31.10.2026)

Цель: запись, после которой запасной блок нельзя «окирпичить». Главная страховка — загрузчик C509 в **ПЗУ процессора** (0000–01FF boot ROM): запись флеш его не трогает, вход по +12 В на 47 работает при любом содержимом флеш, **кроме** образа с действующим инфо-блоком (тогда фаза I запускает код из флеш вместо загрузчика). Поэтому:

1. **Запрет образов с инфо-блоком** (`FlashWriteAgent.refusalReason`: `23 03 33 13` + верная КС области по C000/6000). Скан 75 образов в `firmware/` (31.10): действующего инфо-блока нет ни у одного; байты-признак без верной КС — у 6 образов Январь 7.2 (`A201CO57`, `A204DO57`, `A203EL35-*`, `I203EK33`, `ASUPER11`) по 6000 — не блокируют. Плюс образ с неверной КС ПЗУ не пишется (окно предлагает пересохранить).
2. **ID флеш до записи**: только `01 20` (Am29F010), иначе запись не начинается.
3. **Резервная копия перед стиранием**: агент записи читает текущие 64 КБ, файл `flash_backup_before_write_<дата>.bin` сохраняется **до** первой команды стирания.
4. **Стирание секторами, не всей микросхемой**: Am29F010 — 128 КБ, мы видим окно 64 КБ (A16 = P6.0). Стирание всей микросхемы (`'E'`) уничтожило бы вторую половину, которую мы не читали. Теперь `'S' addrH` — стирание сектора 16 КБ текущей половины; стираются только **отличающиеся** сектора (с флажком «перезаписать все» — все четыре).
5. **DQ5 (отказ микросхемы)**: опрос по алгоритму data polling; при DQ5 агент делает сброс F0, при стирании отвечает `E5`, при записи байта — дочитывает остаток пакета без программирования и отвечает XOR инверсией → понятная ошибка вместо зависания агента или принятия данных за команды.
6. Байты `FF` не программируются (стёртая ячейка уже `FF`), пакеты из одних `FF` не передаются.
7. **Сверка всех 64 КБ** чтением после записи; журнал байтов линии (`TracingTransport`) при любой ошибке.

Эмулятор: модель флеш умеет отказы (`Flash29F010.faultySectors`: DQ5 при записи/стирании). Тесты `FlashWriteTests`: вторая половина не трогается; одинаковый образ не перезаписывается (с `force` — 4 сектора); стираются только отличающиеся сектора; образ с инфо-блоком отклонён до стирания; отказ стирания → `E5`, отказ записи → `programFailed`, агент после этого жив.

**Если запись всё-таки прервётся** (пропало питание, выдернули кабель): блок не запустится, но загрузчик цел — выключить питание, повторить запись тем же окном (источник — резервная копия).
